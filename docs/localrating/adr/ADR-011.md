# ADR-011 – Tenant-scope og isolation

Dato: 2. oktober 2026. Status: **Foreslået** (afventer ejerens godkendelse, Fase 0-gate). Hører til `docs/localrating/README.md`.

## Kontekst
CMS er multi-tenant via `instansId` (tenant fra `Host`/bruger). Spec §28: data fra Instance A må aldrig vises i B. Knowledge OS har ingen isolation i drift.

## Beslutning
1. Alle LocalRating-tabeller har `instansId` + indeks; ingen `instansId = null`-rækker; standardprofiler/-prompter **seedes pr. instans**.
2. `instansId` kommer **altid** fra den indloggede bruger/cron-parameter/`ToolCtx` – aldrig fra klient eller model; fremmed id ⇒ "findes ikke".
3. **DB-niveau:** obligatoriske forældrelinks bruger sammensatte FK'er `(instansId, parentId)` (uverificeret mod `prisma validate`, fallback: bløde pegere + servicetjek); links til eksisterende CMS-tabeller er bløde (Article/GeoTag/Instance uændret).
4. Cache-/dedupe-nøgler indeholder `instansId`; `matchGeo` kun mod instansens GeoTags; Knowledge-kontekst kun for én instans.
5. **Eksplicitte cross-tenant-tests** for alle services/actions/routes/cron/simulator/operatørværktøjer.
6. Ingen hardcodede bynavne i LocalRating (test); kernens hardcodes flages.

## Konsekvenser
+ Stærk isolation med lille kerne-påvirkning.
− Ingen DB-cascade til `Instance`; dangling soft-id ved slettet artikel accepteres.

## Alternativer (fravalgt)
- `Instance`-relationer (back-relations): ændrer `Instance`-modellen; afvist.
- Delte globale profiler/prompter: lækage mellem byer; afvist.
